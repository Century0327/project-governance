# project-governance 动态行为审计报告（审计第二轮）

- 日期：2026-09-10

- 依据：前两轮静态审计（docs/audit-v1.1.0-mechanism-audit.md、docs/change-budget-v1.2.0.md）+ 本轮通读的全部文件

- 方法：不找新的静态问题，改做 **5 个真实任务模拟**，每个任务追踪完整状态流：状态来源 → AI 动作 → 写入什么 → 谁确认 → 下一轮 AI 会把什么当事实 → 出错后能否恢复；并对 8 个新维度逐项评估。

- 立场：审计可以很广，修改必须很窄。本报告产出以"观察项 + 极小候选"为主，不自动扩大 v1.2.0。

***

## 一、任务模拟 1：正常执行（新增文件并登记）

场景：项目新增 `src/utils/helper.py`，AI 按规则执行"文件变动 → 更新 index"。

| 状态流环节    | 推演结果                                                                                                                                               |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| 状态来源     | 文件系统（新文件真实存在）→ index.md 相对磁盘过期（check 应报）                                                                                                           |
| AI 动作    | 规则 7"any file add/remove/move updates index.md"——但**更新方式有两种合法选择**：跑 `index` 命令（重写整树，覆盖人工内容，A-2 未修前）或手动编辑树块（保留人工内容，但缩进/排序未必符合 `_is_index_fresh` 判定） |
| 写入       | CHANGELOG 一条记录（**位置未定义**，A-1：顶部或底部均说得通）；handoff 更新 Last session                                                                                    |
| 谁确认      | **全程无确认点**（除非人主动介入）                                                                                                                                |
| 下一轮事实    | 新 index 树成为下轮 AI 查找的事实源                                                                                                                            |
| 恢复能力     | check 可发现 index↔磁盘不一致（但只报"过期"，无差异清单，A-9a）                                                                                                          |
| **审计发现** | **正常路径本身不稳定**：AI 手动编辑 index 后 check 可能仍判过期（格式不符）；跑 index 则丢人工内容。两种"合法"方式互相冲突，"正常执行"的终态取决于 AI 选了哪条路——这正是 suhu 实证的对抗循环                               |

***

## 二、任务模拟 2：重复执行（同一任务跑两次）

场景：任务"新增并登记 `experiments/foo.md`"连续执行两次。

| 状态流环节         | 推演结果                                                                                                                 |
| ------------- | -------------------------------------------------------------------------------------------------------------------- |
| 第一次           | 文件创建 ✓、index 更新 ✓、CHANGELOG 写 1 条 ✓                                                                                  |
| 第二次           | 文件已存在（创建幂等 ✓）；index 重新生成（内容无变化，命令级幂等 ✓）                                                                              |
| **CHANGELOG** | **会再写一条**——无"该变更是否已记录"的去重检查（语义幂等缺失）                                                                                  |
| handoff       | 可能重复更新（无去重）                                                                                                          |
| LESSONS       | 不涉及（无错误），无风险                                                                                                         |
| 恢复能力          | 无检测手段：check 不校验 CHANGELOG 条目去重                                                                                       |
| **审计发现**      | **命令级幂等 ≠ 语义幂等**（GPT 维度 3 成立）。CLI 层 `init`/`index` 幂等性有测试（A9/C5），但"AI 任务层"无任何幂等保障。重复记录会使 CHANGELOG 与 handoff 膨胀、污染事实 |

***

## 三、任务模拟 3：部分失败（改 A 成功、改 B 成功、改 C 失败）

场景：AI 执行"创建文件 + 更新 index + 更新 CHANGELOG + 更新 handoff"，在更新 CHANGELOG 时失败（格式/磁盘错误），session 结束。

| 状态流环节           | 推演结果                                                                                                |
| --------------- | --------------------------------------------------------------------------------------------------- |
| 已完成             | 文件创建 ✓、index 更新 ✓                                                                                   |
| 未完成             | CHANGELOG ✗、handoff ✗（模板的"Last session"依赖本轮正常写完才存在）                                                 |
| 下一 session 恢复路径 | 读 AGENTS → index.md（已更新，看到新文件）→ session\_handoff.md（**无"欠 CHANGELOG 一条"的任何痕迹**）                     |
| 能否恢复            | **不能**。check 不检查 CHANGELOG 完整性（A-9 假检查），新 session 无从得知"记录欠账"                                        |
| **审计发现**        | **无 transaction/checkpoint/欠账恢复机制**（GPT 维度 4 成立）。部分失败状态静默丢失。CLI 命令本身有异常处理（HINT），但**跨文件的"任务级"原子性为零** |

***

## 四、任务模拟 4：session 中断恢复（执行到 40% 强制中断）

场景：任务"实现功能 X"进行到 40%（代码改了一半，文档未动），session 被强制中断。新 session 只读治理文件。

| 状态流环节          | 推演结果                                                                                                                 |
| -------------- | -------------------------------------------------------------------------------------------------------------------- |
| handoff 实际内容   | 模板只有 Last session / Pending / Next steps / Notes；**若中断前 AI 未更新 handoff（模板未要求任务开始时写"进行中任务/完成度/确认状态"），新 session 完全失明** |
| 新 session 恢复手段 | 只能从代码状态（改了一半的文件）与 index（未更新，因任务未完成）猜测——**无法恢复进行中任务**                                                                 |
| 恢复能力           | 依赖 AI 运气与人工记忆，不依赖系统                                                                                                  |
| **审计发现**       | **handoff 被当作"文件太大"问题处理是可惜的——它本是核心恢复机制**（GPT 维度 5 成立）。缺字段：当前进行中任务、完成度、已确认/草案区分、中断原因。模板未要求"任务开始时先登记"，导致中断时必然失明        |

***

## 五、任务模拟 5：AI 错误推断写入 canonical state

场景：AI 推断"这个文件应该就是架构文档"，把推断写入 ARCHITECTURE.md（模板占位符未填，A-5a 未修时尤易发生）。

| 状态流环节    | 推演结果                                                                                                                               |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 写入       | AI 直接填充 `{{ARCHITECTURE_OVERVIEW}}`（无"草案"标记）                                                                                       |
| 下一轮事实    | 新 session 按 Layered Context Tier 2 读 ARCHITECTURE.md，**把 AI 推断当项目事实**                                                              |
| 错误强化     | 推断 → 持久化 → 当事实 → 基于错误事实决策 → 错误证据进入更多文件                                                                                             |
| 现有防护     | **无**：无"推断/草案/已确认"的认知状态（epistemic status）标记；index\_notes 备注同样无来源区分                                                                 |
| **审计发现** | **"AI 猜测 → 持久化 → 未来 AI 当事实"的自强化循环无任何防线**（GPT 维度 6 成立）。与用户关注的"外部记忆不因被写入而自动获得真实性"直接相关。architecture 的"A 草案→人确认"只解决了产生方式，未解决写入后的认知状态标记 |

## 六、8 个新维度评估结论

| # | 维度                         | 结论       | 现有机制                                | 缺口                                                                   |
| - | -------------------------- | -------- | ----------------------------------- | -------------------------------------------------------------------- |
| 1 | 规则优先级（authority hierarchy） | **部分成立** | AGENTS.md 内有权威优先级 1-5（模板含"记忆与治理边界"） | **跨文件层级无定义**：SKILL vs AGENTS vs README vs CLI help 冲突时听谁的，无文档化优先级    |
| 2 | 状态转换（演化/失效/替换/恢复）          | **成立**   | 无                                   | 只审了"状态怎么产生"，未审"怎么演化、失效、被替换"；architecture 被人工修改后，无"过时判定/谁可改/保留人工修改"规则 |
| 3 | 重复执行语义幂等                   | **成立**   | CLI 命令幂等（有测试）                       | AI 任务层无幂等：CHANGELOG/handoff 重复写无去重                                   |
| 4 | 部分失败恢复                     | **成立**   | CLI 单命令异常处理（HINT）                   | 跨文件任务级无 checkpoint；欠账不可恢复                                            |
| 5 | session 中断恢复               | **成立**   | handoff 存在                          | 缺"进行中任务/完成度/确认状态"字段；无任务开始登记要求                                        |
| 6 | 认知状态（事实/推断/草案）             | **成立**   | 无                                   | 推断与确认状态无标记；写入即获得事实地位                                                 |
| 7 | self-modifying governance  | **成立**   | AGENTS 有"不经批准不得修改"（文字）              | 哪些治理文件 AI 可改、改后何时生效、是否需批准/重跑 tests/版本化——全部未定义；B-1 指令冲突放大该缺口          |
| 8 | 规则膨胀/相互遮蔽                  | **成立**   | 无                                   | 规则持续增加（suhu AGENTS 已很长），无"核心 invariant vs 例外"划分，重点规则被淹没的风险真实         |

## 七、对 v1.2.0 的影响（克制评估）

**原则不变：审计可以很广，修改必须很窄。** 动态行为审计的发现主要进入观察项，极小候选如下：

### 进入 v1.2.0 的极小候选（建议 2 项，均为纯模板/文档，低风险）

| 候选                             | 针对           | 最小方案                                                                                       | 风险                  |
| ------------------------------ | ------------ | ------------------------------------------------------------------------------------------ | ------------------- |
| **H-1 handoff 模板增加"进行中任务"登记行** | 任务 4（中断恢复失明） | 模板顶部加一行 `- 当前进行中任务：{描述/进度/已确认项}`，并写明"任务开始时先登记，结束或中断时更新"（纯模板+SKILL 一句）                      | 低：不改变任何行为，只补字段      |
| **H-2 认知状态标记（草案/已确认）**         | 任务 5（推断自强化）  | ARCHITECTURE.md 模板占位符区加固定标注"本段为草案（AI 推断，未经人确认）→ 人工确认后移除标注"；AGENTS 规则补一句"AI 写入推断性内容必须带草案标记" | 低：模板+规则一句，不改 schema |

### 明确不进入 v1.2.0（观察项，留待真实事故证据）

- **语义幂等**（任务 2）：CHANGELOG 去重需要"变更指纹"机制，涉及 schema/行为（高成本），观察。

- **部分失败/checkpoint**（任务 3）：需事务设计，远超本轮范围，观察（与 C-3 树膨胀同属长期项）。

- **authority hierarchy 跨文件文档化**（维度 1）：有价值但需先在 DESIGN 明确层级模型，建议在 ADR（批准边界/所有权）中作方向性记录，不单独改动。

- **self-modifying 完整机制**（维度 7）：需版本化+测试门禁设计，观察。

- **规则膨胀治理**（维度 8）：可作 DESIGN 方向（引入"核心 invariant 清单"），不实施。

***

## 八、核心结论

1. **动态行为审计证实：系统最薄弱的不是"规则缺失"，而是"执行轨迹不可恢复"**——重复执行会污染、部分失败会丢欠账、中断会失明、错误推断会自强化。
2. **四条防线全部缺失**：语义幂等（去重）、checkpoint（欠账记录）、中断恢复（进行中任务字段）、认知状态（草案/确认标记）。这四条都是"机制性"问题，但**修复成本依次升高**。
3. **与静态审计的关系**：静态审计发现的是"规范自由度"（AI 选哪个都行），动态审计发现的是"轨迹不可恢复"（选了之后回不去）。后者对长期 agent 项目更致命——与用户"AI 遗忘 + 交接"的核心关切直接对应。
4. **v1.2.0 边界维持**：12 项已裁定范围不变；本报告仅建议新增 2 项极小候选（H-1/H-2，纯模板/文档）。其余全部留观察项，不因"机制化思考"扩大版本。
