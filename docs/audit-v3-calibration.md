# 审计结果校准报告（第三轮：防过度设计）

- 日期：2026-09-10

- 依据：docs/audit-v2-dynamic-behavior.md 的发现 + 规范原文核实（SKILL.md 使用步骤/命令示例、AGENTS.md 规则 7、README FAQ）

- 目的：不扩大问题清单，只复核现有发现是否存在**过度归因 / 过度设计**，并给出收窄后的 v1.2.0 实施边界。

- 原则：v1.2.0 只修"有真实证据 + 明确最小修复方案"的问题；依赖语义定义/真实事故/更多使用数据的问题继续留观察项。

## 复核点 1：任务 1"多路径"归因修正（原 A-2 的表述有偏）

**原发现**："手动编辑 index / 跑 index 都是合法选择，正常路径不稳定"。

**规范原文核实**：

- SKILL.md 使用步骤 3："更新 `session_handoff.md`、`index.md`（文件变动）、`CHANGELOG.md`（决策）"——只说更新，不说方式。

- SKILL.md/README 命令示例：`governance.py index`（重建 index.md 目录地图）。

- SKILL.md 故障处理："check 失败（索引过期）：先运行 index，再重跑 check"。

- AGENTS.md 规则 7："Any file add/remove/move updates index.md"——只说更新，不说方式。

- check 的 `_is_index_fresh` 判定隐含"index 内容必须等于命令生成的内容"。

**校准结论**：

- **规范从未声明"手动编辑 index 是合法路径"**——规范只提供了 index 命令这一种工具，只是**从未显式声明"index.md 树块由命令独占维护、手动编辑不被支持"**。

- 更准确的归因是：**维护方式（canonical procedure）未显式化**，check 行为隐含"只认命令格式"，但文档从未说明 → AI 手动编辑后 check 判过期，属于"规范没说，AI 自行选择"，**不是规范允许两路**。

- 修复不是"定义两种方式"，而是**显式化"index 树块由 index 命令独占维护；人工补充进 index\_notes.json 或自定义 section（需保护）"**。

- **A-2 保护仍然成立**：suhu 用户确实人工编辑过 index（注释/调整），"只支持命令"与真实用户需求冲突，故"检测人工内容→默认停止+告警，--force 才覆盖"是必要的产品决策（中间路线）。

- **边界影响**：A-2 保留，附一句"维护方式显式化"文档；无新增项。

## 复核点 2：语义幂等——先定义语义，不做指纹机制

**原发现**："同一任务执行两次会重复写 CHANGELOG，语义幂等缺失"。

**语义核实**：

- 模板：CHANGELOG "Records decisions and outcomes"（决策与结果）

- SKILL.md：记录决策与版本历史；README：项目为什么变成现在这样

- AGENTS 规则 7："any decision updates CHANGELOG.md"

**校准结论**：

- CHANGELOG 的语义是**决策 / 状态变化**，不是事件日志。同一决策被重复执行（第二次无新决策、无新状态变化）时，确实不应产生第二条记录。

- 但**不需要"变更指纹/dedup schema"**（过早设计机制）。

- 最小修复：A-1 配套加一句**语义定义 + AI 自查**："CHANGELOG 记录决策与状态变化，非事件日志；记录前先检查该决策是否已记录，已有则不再重复"（文档级，AI 层自查）。

- **边界影响**：并入 A-1；指纹机制明确不做，留观察。

## 复核点 3：原子性 vs 可恢复性——真实需求是后者，H-1 已覆盖

**原发现**："部分失败需要 transaction/checkpoint"（表述跃进）。

**校准结论**：

- 真实需求是**可恢复性**（任务做了一半，下个 session 知道完成/欠账），**不是多文件原子提交**。

- 最小方案就是 H-1 的形态：handoff 登记"当前进行中任务 + 逐项完成状态"（`[x] create file / [x] update index / [ ] update changelog`）。

- **事务系统明确不设计**；checkpoint 机制不引入。

- **边界影响**：H-1 保留（它就是可恢复性最小方案）；"部分失败需事务"从 v1.2.0 移除。

## 复核点 4：H-2 收窄——只修 architecture 场景，不做通用 epistemic schema

**原发现**："AI 推断写入即获事实地位，需草案标记"（表述过宽）。

**校准结论**：

- 不能要求"所有 AI 写入内容都带草案标记"——文件系统事实（`src/utils/helper.py` 存在）、用户声明等不需要。

- 当前**唯一真实案例是 ARCHITECTURE.md / PROJECT.md 的模板占位符**（AI 填 `{{...}}` 后无"未经确认"标记）。

- 最小修复：**只在 ARCHITECTURE/PROJECT 模板占位符区加固定标注**"本区为模板占位：由 AI 根据项目事实提出草案，经人工确认后生效；未经确认不得视为项目事实"——**与 A-5a（占位符模板示例化）合并执行**。

- **通用 epistemic-status 分类系统（文件系统事实/用户声明/AI 推断/建议/已确认 的分类 schema）明确不做**，留观察。

- **边界影响**：H-2 不再单独立项，**并入 A-5a**。

## 复核点 5（新维度）：最小变更 / 禁止多余修改（scope creep）

**风险识别**（只识别，不设计复杂机制）：

- 模拟"用户只要求：新增一个文件并登记"：

  | 治理文件                                     | 是否需要动 | 依据                               |
  | ---------------------------------------- | ----- | -------------------------------- |
  | index.md                                 | ✅ 需要  | 规则 7 明确要求（文件变动→index）            |
  | session\_handoff.md                      | ✅ 需要  | After Completing a Task / 会话结束更新 |
  | CHANGELOG.md                             | ⚠️ 灰色 | "文件新增"是否构成"决策"未定义；纯登记不需，AI 可能顺手写 |
  | LESSONS.md                               | ❌ 不需要 | 只在犯错时写                           |
  | VERSIONS.md                              | ❌ 不需要 | 只在版本变化时写                         |
  | ARCHITECTURE.md / PROJECT.md / README.md | ❌ 不需要 | 文件登记不涉及                          |

- **风险**：After Completing a Task 列 8 步更新，无"仅做必要更新"约束；AI 可能连锁修改大片状态文件（与用户"谨慎审批"关切直接相关）。

- **最小修复**：AGENTS 模板补一句**最小更新原则**："治理文件只更新任务需要 + 规则明确要求的（index / CHANGELOG / handoff）；其余治理文件（README / ARCHITECTURE / PROJECT / LESSONS / VERSIONS）非必要不动"（规范一句，低风险，无真实事故证据 → 归"建议修"）。

- **边界影响**：新增 M-1 项（模板一句）。

## 收网结论

1. 三轮审计形成完整闭环：**第一轮防漏（静态规范自由度）→ 第二轮防过拟合（change-budget 收敛）→ 第三轮防过度设计（校准归因与机制）**。
2. v1.2.0 从最初的"10 个已知问题补丁"收敛为 **14 项最小充分修复**：7 必须修 + 6 建议修 + 1 handoff 项，全部为模板/文档/告警级改动，唯一行为变更是 A-2（防数据丢失）。
3. 审计发现的机制类问题（语义幂等、可恢复性、认知状态）**用最小方案就地解决（自查句 / H-1 / 局部标注），不建立对应机制系统**——满足"审计可以很广，修改必须很窄"。
